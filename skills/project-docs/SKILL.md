# project-docs：每個專案一套

先確認需求、長出骨架、定好每個檔案的分層、寫執行計畫，最後才寫程式。三四輪功能之後重構，定期清技債。
這不是新觀念，難的是**讓每一個新開的對話、每一個工人都照做**。所以寫成檔案放在 repo 裡，讓它們一進來就讀得到。

## 四份文件（範本在 `templates/`，放 repo 的 `docs/`）

| 檔案 | 寫什麼 | 誰寫 |
|---|---|---|
| `PRD.md` 需求 | 給誰、解決什麼、主打、加分、不做／做不到、上線要過的、還沒定的 | 總指揮從使用者的原話整理，**使用者改過才算數** |
| `ARCHITECTURE.md` 骨架 | 資料夾放什麼、資料怎麼流、太肥的檔怎麼拆、分層規矩 | 工人量、總指揮審 |
| `PLAN.md` 計畫 | 一步一步，每步：動哪些檔、怎麼驗收；最後列「要使用者決定的」 | 總指揮 |
| `TECH-DEBT.md` 技債 | 檔名:行號、是什麼、為什麼算債、怎麼還、大小；先還的五條 | 工人列、總指揮排序 |

在 repo 的 `CLAUDE.md`（或 `AGENTS.md`）開頭加一句：
> 開工前先讀 `docs/` 的四份文件；做完更新 PLAN（這步做完了）跟 TECH-DEBT（還了哪條、新增哪條）。

## 新專案

1. 先寫 PRD 跟 PLAN 給使用者看，點頭才往下
2. 骨架跟分層規矩先定（例如：畫面檔不放資料讀寫、單檔超過 400 行就要登記拆）
3. 才開始寫程式

## 舊專案第一次建檔

1. 派一張**只讀**的盤點工單（範本：`templates/AUDIT-BRIEF.md`）：量每個檔案多大、畫骨架、列技債，不改任何東西
2. 總指揮從過去的對話、筆記整理 PRD 草稿，排 PLAN
3. 四份一起給使用者看，改完再派一張寫進 repo、開 PR

## 重構的節奏

- **每加三四個功能，排一輪重構**，寫進 PLAN。
- 重構那輪**不加功能**，從技債清單挑來還；驗收是「行為不變、測試全過」。
- 一個檔案大到 agent 一讀上下文就爆，每次讀都是在幻覺區做事。下一個功能要動到的肥檔，**在做功能之前先拆**。
