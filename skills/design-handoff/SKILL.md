# design-handoff：設計怎麼交接才不會走樣

設計最常死在兩個地方：使用者腦中的畫面被轉述成規格的那一步，跟「看起來差不多」的驗收。

## 1. 先做可以點的草圖

版面、動態，先做一頁可以在手機上點的 HTML 草圖給使用者玩，改到對了才寫施工圖。
- 不要用生圖模型畫介面：它畫得很漂亮，但按鈕位置、比例都是自己長的，看了反而更難討論。
- 草圖要真的會動，動態才有得討論。
- 草圖原始檔存進 repo。

## 2. 說出「那一下」

每次改版點名一個會動、會回應的地方。只說「收斂、精緻、乾淨一點」，得到的只會是減法：外框拿掉、圓角縮小、形狀從參考搬過來了，動作沒搬。

## 3. 幫效果取名字

使用者描述了一個效果、你第一次聽不懂的時候，問清楚之後**一起定一個名字**，寫進專案的 `docs/DESIGN-TERMS.md`（範本：`DESIGN-TERMS.md`）。下次一句話就對得上。
每個名字寫：是什麼、不是什麼（你第一次做錯成什麼）、怎麼開口說、可以調的參數。

範例：**拆件動態圖示**——線條圖示拆成幾個零件，點下去時每個零件照它代表的意思動（鎖頭的彎鉤扣下去、抽屜拉出來），動完回原位。不是整顆圖示一起縮放、旋轉或重畫一次。

## 4. 美術指導跟施工分開

最懂審美的模型通常也最貴。讓它只做這件事：
1. 給它使用者的原話、參考圖、現在的程式片段或截圖
2. 只問：這頁要給人什麼感覺？現在哪裡不對？要怎麼改？
3. 它不寫程式
4. 總指揮把它的想法翻成數字（用 `brief`），交給便宜的工人做
5. 做完把截圖或錄影給它看一次：跟你想的一樣嗎？

## 5. 驗收

- 會動的東西錄影，截圖看不出節奏
- 手機尺寸、深淺色、減少動態各看一次
- 拿使用者的原話逐句對成品，不是對工人的回報
